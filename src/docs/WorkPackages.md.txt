# Work Packages and Defined Demand

AMO uses **Defined Demand** as the parent portfolio boundary and **Work Packages** as the delivery decomposition beneath it.

A Work Package stores only the metadata required for portfolio management: title, Architecture Service, delivery status, estimated effort, target dates and backlog work-item reference. Detailed scope and acceptance criteria remain in the authoritative delivery backlog.

```text
Defined Demand
├─ Initial ROM
├─ Budget Forecast
├─ Project Number / Actuals identity
└─ Work Packages
   ├─ WP Estimate
   └─ Resource Plan allocations
      └─ Person × Work Package × Month
```

## Defined Demand boundary

Demand owns:

- portfolio identity and lifecycle;
- Initial ROM (`initialEstimate`);
- current Budget Forecast (`budgetForecast`);
- Project Number used for Oracle Actuals reconciliation;
- parent ownership/context.

Budget Forecast is the current forecast for budgetary and portfolio-planning purposes. It is **not** an approved financial budget and is not changed automatically by Work Package estimates or allocations.

Demand does not own Architecture Service, detailed delivery scope, delivery dates or Work Package delivery status.

## Work Package record

Current Work Package fields include:

- `id`;
- `demandId`;
- `title`;
- `service`;
- `status`;
- `estimatedEffortDays`;
- `targetStart` / `targetEnd`;
- `azureDevOpsWorkItemId`;
- version/modified metadata.

Work Package Estimate is a delivery estimate. It does not overwrite Demand ROM or Budget Forecast.

## Planning progression

AMO keeps the planning stages separate:

```text
Initial Demand ROM
        ↓
Demand Budget Forecast
        ↓ compare
Work Package Estimate
        ↓ compare
Work Package Resource Plan
        ↓
Actual to date + remaining plan
        = Projected effort
```

Demand Resource Plan is derived by rolling up allocations across child Work Packages.

## Resource and Actuals boundary

Steady-state allocations are:

```text
Person × Work Package × Month
```

Each allocation also retains `demandId` as parent/query context, and the referenced Work Package must belong to that Demand.

Existing records without `workPackageId` are transitional **legacy / undecomposed allocations**. They remain visible and reportable until explicitly assigned to a Work Package. AMO never guesses or silently assigns their Work Package.

Oracle Actuals remain:

```text
Person × Project Number × Month
          ↓
Demand.projectNumber
          ↓
Defined Demand
```

AMO does **not** infer Work-Package-level Actuals. Work Package reporting may show the retained plan for an Actual period, but must state that Actuals are held at parent Demand.

## Demand Register and Allocations experience

The Demand Register manages the parent/child delivery structure. Demand rows contain nested Work Packages and Work Packages are created/edited from that hierarchy.

The Allocations view manages resource planning as:

```text
Demand
  ↓
Work Package
  ↓
Person
  ↓
Monthly allocation
```

New named-person allocations can only be created beneath a Work Package. Legacy Demand-only allocation records appear in an explicit undecomposed section and can be migrated to a valid child Work Package.

## Reporting

Demand reporting presents:

- Initial ROM;
- Budget Forecast;
- Work Package Estimate + estimate coverage;
- Resource Plan;
- Actual to date;
- Projected effort;
- material comparison signals.

Work Package reporting presents its Estimate and Resource Plan only. Actuals remain at Demand/Project level.

## Backlog reference

AMO stores an Azure DevOps Work Item Reference on the Work Package and derives the link from inherited System / Department / Team configuration. The delivery backlog remains authoritative for detailed work definition.

## Migration principles

Migration preserves history without inventing relationships:

- old Demand Service remains history and is not copied to every Work Package;
- old Demand ROM becomes the initial estimate where meaningful;
- old Demand dates remain history and do not drive the current Roadmap;
- legacy Deliverables are not silently converted into Work Packages;
- legacy Cost Centre / Project Code is not promoted to Project Number;
- legacy Demand-only resource allocations remain explicit undecomposed allocations until a user assigns them to a Work Package.

## System responsibilities

- **SharePoint Front Door** — authoritative intake/source for Raw Demand;
- **Azure DevOps / Jira** — authoritative delivery backlog/work-item detail;
- **AMO** — Defined Demand, Work Package portfolio metadata, Budget Forecast, Work Package Resource Plan and Actuals reconciliation.

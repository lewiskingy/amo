# Work Packages and Defined Demand

AMO uses **Demand** as the persisted name for the recognised body of Architecture work under management. Conceptually this is **Defined Demand**: it can exist while scope or ROM is still being established and it does not have to be a funded Project.

A **Work Package** is a discrete delivery package beneath Defined Demand. It describes a tranche of work that can be estimated, given acceptance criteria, tracked and linked to an Azure DevOps work item without changing the resource/accounting boundary of the parent Demand.

```text
Raw Demand (SharePoint Front Door)
        ↓
Triage (AMO + Azure DevOps)
        ↓
Defined Demand (AMO Demand)
        ├─ Work Package → Azure DevOps Work Item
        ├─ Work Package → Azure DevOps Work Item
        ├─ Allocations
        └─ Actuals ← Oracle Project Number
```

## Work Package record

Work Packages are first-class records stored separately from Demand. The initial record contains:

- `id` — stable Work Package ID;
- `demandId` — required parent Demand;
- `title`;
- `description` — delivery scope/description;
- `acceptanceCriteria`;
- `status`;
- `romDays`;
- `targetStart` and `targetEnd`;
- `azureDevOpsWorkItemId` — optional numeric Azure DevOps Work Item Reference;
- record version/modified metadata.

Local workspaces store one JSON document per Work Package under `work-packages/`. Remote/Mongo workspaces use the same logical `workPackages` entity through the repository/API boundary. Application code uses the shared WorkspaceRepository contract for both storage modes rather than maintaining a separate Local implementation.

Work Packages deliberately do **not** own Allocations or Actuals. Allocations remain Person × Demand × Month. Oracle Actuals remain Person × Project Number × Month and reconcile through the optional unique Project Number on Demand. This keeps Plan versus Actual at the same management/accounting boundary.

Demand-level ROM, dates and scope remain present for now. A later refinement may deliberately derive or aggregate some of those values from child Work Packages; Step 3 does not invent that aggregation before its semantics are agreed.

## Demand record experience

Work Packages are managed as children of their parent Defined Demand. Double-click a Demand in the Demand Register to open its record; the same record view contains the Work Packages section and the actions to add, edit or delete child packages.

The previous interaction in which a single click silently selected a Demand and rendered a separate detail/Work Package area at the bottom of the Demand page has been retired. There is no separate bottom-of-page Work Package management surface and no selected-Demand state is required to discover the child records.

This keeps the interaction aligned with the domain model:

```text
Open Defined Demand
        ↓
Demand details
        ↓
Child Work Packages
        ↓
Azure DevOps Work Item
```

## Azure DevOps reference and inheritance

A Work Package stores only the Azure DevOps **Work Item Reference** (the numeric work item ID). AMO derives the URL from inherited organisational configuration instead of persisting a full environment-specific URL on every Work Package.

Organisation resolution is:

```text
Team Organisation override
        ↓ otherwise
Department Organisation override
        ↓ otherwise
System Default Organisation
```

Project resolution is:

```text
Team Project override
        ↓ otherwise
Department Default Project
```

Blank override fields mean **inherit**. Inherited values are not copied into child settings, so changing a Department or System default genuinely cascades to records that have not overridden it.

AMO does not guess an organisational context when a Demand does not resolve to a Team/Department. If no applicable Department/Team is available, the Azure DevOps link remains unavailable until the context is configured explicitly.

With an effective Organisation, Project and Work Item Reference, AMO derives:

```text
https://dev.azure.com/{organisation}/{project}/_workitems/edit/{workItemId}
```

A Work Package may retain its Work Item Reference when the effective Organisation or Project is not yet configured; AMO simply cannot produce the hyperlink until the inherited context is complete.

## Canonical Azure DevOps relationship

The Work Package is the canonical AMO relationship to an Azure DevOps Feature/Epic/work item. The older Demand-level Azure DevOps URL/title relationship is retired in Step 3: it is no longer displayed or editable, and Demand records saved through current UI paths remove that obsolete property rather than perpetuating two competing linkage models.

This also means Allocations, Resource Plan and Roadmap no longer surface an inherited Demand-level “Work Item” link. Where delivery-item context is needed, it should come from the Work Packages belonging to the Demand.

## Process responsibility

The intended responsibility split is:

- **SharePoint Front Door** — authoritative intake/source for Raw Demand;
- **Azure DevOps** — triage/backlog and delivery work-item tracking;
- **AMO** — Defined Demand, Work Packages, portfolio/resource planning and Actuals reconciliation.

During triage, a request may be recognised as a genuinely new body of work and a Defined Demand can be created before ROM, final scope or Project Number is known. If the request belongs to existing Defined Demand, it should normally become or amend a Work Package beneath that Demand rather than create duplicate Demand.

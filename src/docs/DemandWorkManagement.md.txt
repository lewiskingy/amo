# Demand Work Management

This guidance defines how SharePoint Front Door, Azure DevOps and AMO work together.

## Working model

```text
Raw Demand
SharePoint Front Door
      ↓
Triage
      ↓
Defined Demand
AMO portfolio boundary
      ├─ Initial ROM
      ├─ Budget Forecast
      ├─ Project Number / Actuals identity
      └─ Work Packages
         ├─ delivery estimate
         └─ named-person Resource Plan
```

**Defined Demand** is the recognised portfolio boundary. It may exist before a Project Number, final Owning Team, committed dates or complete delivery decomposition are known.

**Work Package** is a discrete delivery tranche beneath Defined Demand. AMO stores portfolio metadata only; detailed delivery description/scope and acceptance criteria remain in the authoritative delivery backlog.

## Creating and decomposing Demand

Initial Demand creation is deliberately lightweight. Title and Business Area are the only mandatory user-entered fields; lifecycle state is defaulted.

For each new request, first decide whether the work belongs to existing Defined Demand. If yes, add or amend the appropriate Work Package rather than creating duplicate Demand. If no, create a new Defined Demand and add Work Packages as delivery understanding develops.

## Planning progression

AMO deliberately retains each level of planning knowledge:

```text
Initial ROM
    ↓
Budget Forecast
    ↓ compare
Work Package Estimate
    ↓ compare
Work Package Resource Plan
    ↓
Actual to date + remaining Resource Plan
    = Projected effort
```

### Initial ROM

The early assessment baseline. It remains separately reportable.

### Budget Forecast

The current effort forecast for budgetary and portfolio-planning purposes. It may change as understanding improves. It is **not** an approved financial budget and does not automatically change Work Package estimates or allocations.

### Work Package Estimate

The current delivery estimate of an individual Work Package. Demand WP Estimate is the sum of populated child estimates, with estimate coverage retained.

### Work Package Resource Plan

New allocations are created only against Work Packages:

```text
Person × Work Package × Month
```

`demandId` remains parent context and must match the Work Package's parent Demand. Demand Resource Plan totals are derived roll-ups across child Work Packages.

Existing Demand-only allocations remain supported only as explicit legacy / undecomposed transition records. They are never silently assigned to a Work Package.

### Actuals and projected effort

Oracle Actuals remain observed Demand/Project facts:

```text
Person × Project Number × Month
          ↓
Demand.projectNumber
```

Actuals are not inferred at Work Package level.

For an imported month, Actuals are the reported value; otherwise Allocation Forecast is used. Across the horizon:

```text
Actual to date + remaining Allocation Forecast = Projected effort / cost
```

Projected effort is compared with Budget Forecast using wording such as **above Budget Forecast**, not “over budget”.

## Resource and financial semantics

Allocation values are fractions of a Person's available FTE:

```text
Forecast FTE = allocation fraction × Person FTE
```

Forecast days/cost are valued using the Person's Role day rate, with the configured blended/default rate as fallback. Initial ROM, Budget Forecast and Work Package estimates may use the blended/default rate for indicative valuation. Imported Oracle Actual cost is authoritative and never recalculated from AMO rates.

## Service, status and dates

Architecture Service, delivery Status and target dates are Work Package concerns. Demand delivery window is derived from child Work Package dates. Defined Demand does not own current delivery dates.

## Resource planning UX

The canonical allocation path is:

```text
Demand
  ↓
Work Package
  ↓
Person
  ↓
Monthly allocation
```

The Allocations view shows Demand planning context, child Work Package estimates and Resource Plan totals. Legacy undecomposed allocations are shown separately and can be explicitly migrated to a valid child Work Package.

## Reporting and management signals

Demand reporting shows ROM, Budget Forecast, WP Estimate, Resource Plan, Actual to date and Projected effort together, while preserving their distinct meanings.

Management signals highlight:

- missing Budget Forecast;
- incomplete WP estimate coverage;
- material WP Estimate variance against Budget Forecast;
- material Resource Plan variance against Budget Forecast;
- material Projected variance against Budget Forecast;
- legacy undecomposed allocations.

Status Report snapshots persist report-time planning context. Historical published reports therefore do not read live planning values later.

## Recovery semantics

Project Number remains the cross-charge/reconciliation indicator.

- **Capacity value** — theoretical value of available People capacity;
- **Forecast recovery** — value of named Resource Plan allocations on Project-backed Demand;
- **Actual recovery** — imported Oracle cost on Project-backed Demand.

## System responsibilities

- **SharePoint Front Door** owns intake and the authoritative Raw Demand source record.
- **Azure DevOps / Jira** owns detailed delivery backlog content and work tracking.
- **AMO** owns Defined Demand, Budget Forecast, Work Package portfolio metadata, Work Package Resource Plan, portfolio/resource reporting and Actuals reconciliation.

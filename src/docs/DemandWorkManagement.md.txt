# Demand Work Management

This guidance defines how the Architecture team should use the Front Door, Azure DevOps and AMO together.

## Working model

```text
Raw Demand
SharePoint Front Door
      ↓
Triage
AMO + Azure DevOps
      ↓
Defined Demand
AMO portfolio boundary
      ↓
Work Packages
Architecture delivery packages / Azure DevOps work items
```

**Raw Demand** is an incoming request that has not yet been qualified into a managed body of Architecture work.

**Triage** assesses whether Architecture involvement is required, whether the request belongs to existing managed work, likely priority, approximate size and capacity implications. AMO can support this assessment alongside Azure DevOps; it does not replace the Front Door or create another intake backlog.

**Defined Demand** is the recognised portfolio boundary represented by an AMO Demand record. It exists to make work visible and manageable early. It does not mean detailed scope is finished and it does not require a Project Number, final Owning Team, committed dates or a fully decomposed delivery plan.

**Work Package** is a discrete delivery tranche beneath Defined Demand. Work Packages carry Architecture Service, delivery scope, acceptance criteria, refined estimate, dates/status and the Azure DevOps Work Item Reference.

## Creating Defined Demand

The initial record is deliberately lightweight. The user must provide only:

- **Title**;
- **Business Area**.

Demand State defaults to the configured initial state (normally **Assessing**). The following are optional and can be added as the demand matures:

- Initiative;
- Owning Team;
- Priority;
- Initial Size (XS/S/M/L/XL);
- Architecture Owner;
- Project Number;
- Health;
- Summary / Context;
- Front Door source/reference.

This allows AMO to provide early portfolio visibility without pretending that triage has already produced a committed delivery plan.

## Triage decision

For each Raw Demand item, first decide whether the work belongs to an existing Defined Demand.

- If **yes**, add or amend the appropriate Work Package beneath that Demand rather than creating duplicate Demand.
- If **no**, create a new Defined Demand and then define the Work Package(s) needed to deliver it when sufficient information exists.

The relationship is not one Front Door request = one AMO Demand. Several requests can contribute Work Packages to the same Defined Demand.

## Initial ROM versus refined estimate

Defined Demand uses deliberately coarse **T-shirt sizing** for the initial ROM. Configuration supplies default day values for XS/S/M/L/XL. When a size is selected, AMO snapshots the corresponding day estimate onto that Demand. This preserves the assumption made at the time of assessment even if the sizing defaults change later.

Work Packages use **Estimated Effort (days)**. Those estimates are the refined delivery view and can be rolled up to show current estimated effort for the Defined Demand.

The measures therefore represent different levels of confidence:

```text
Initial Demand ROM
        ↓
Work Package Estimated Effort
        ↓
Allocation Forecast
        ↓
Actual Effort
```

Do not overwrite the initial ROM with the later Work Package estimate; the difference is useful management information.

## Service, status and dates

Architecture **Service** is a Work Package attribute, not a Defined Demand attribute. A single Defined Demand can contain Strategy, Design, Consultancy and Assurance packages, so a single Demand-level Service would be misleading.

Defined Demand **State** describes the portfolio lifecycle. The canonical states are:

- Assessing;
- Defined;
- Planned;
- In Progress;
- On Hold;
- Complete;
- Cancelled.

Work Package **Status** describes delivery progress and is configured separately (for example Planned, Ready, In Progress, Blocked, Complete, Cancelled).

Target Start and Target End are authored on Work Packages. The Demand-level Roadmap delivery window is derived from the earliest child start and latest child end. Defined Demand does not own committed delivery dates.

## Managing Work Packages in AMO

Open a Defined Demand from the Demand Register to manage its child Work Packages in the same record view. Work Packages are not selected or edited through a separate bottom-of-page panel.

The Work Package is the place for:

- Architecture Service;
- Description / delivery scope;
- Acceptance Criteria;
- Estimated Effort (days);
- delivery Status;
- Target Start / Target End;
- Azure DevOps Work Item Reference.

## Planning and reporting boundaries

Work Packages explain **what is being delivered**. Allocations explain **how much Person capacity is planned against the Defined Demand**. Actuals explain **how much effort was recorded against the Oracle Project Number associated with that Defined Demand**.

Allocations and Actuals remain at Defined Demand level. Step 4 does not alter their record keys or Plan-vs-Actual semantics:

```text
Allocation Forecast
Person × Defined Demand × Month

Actuals
Person × Project Number × Month
          ↓
Demand.projectNumber
          ↓
Defined Demand
```

Where an Actuals period exists it remains authoritative; allocation forecast remains the measure for periods without Actuals/future periods. AMO does not manufacture Work-Package-level Actuals.

## Migration from the older Demand model

Existing workspaces are migrated to schema 3 when opened by a compatible client. Migration preserves information without inventing relationships:

- legacy Demand Service is retained as history but is not copied to Work Packages;
- legacy triage ROM is retained as the Initial Estimate and mapped to the nearest T-shirt size where needed;
- legacy triage summary and Demand scope/objective are consolidated into Summary / Context;
- legacy `workPackage.architectureOwner` becomes Demand `ownerId`;
- legacy Demand dates are retained only as history; they do not drive the current Roadmap;
- legacy Deliverables are retained as history and are not silently converted into Work Packages;
- legacy Cost Centre / Project Code is not migrated into Project Number.

Current saves remove the retired operational fields from the current Demand representation; historical source values are kept under `legacy` only where they are worth retaining.

## System responsibilities

- **SharePoint Front Door** owns intake and the authoritative Raw Demand source record.
- **Azure DevOps** owns backlog/triage and delivery work-item tracking.
- **AMO** owns Defined Demand, Work Package context, resource allocations, portfolio reporting and Actuals reconciliation.

AMO stores only the Azure DevOps Work Item Reference on a Work Package. Organisation and Project are inherited from System, Department and Team configuration; if the Defined Demand has no Owning Team, AMO does not guess that context.

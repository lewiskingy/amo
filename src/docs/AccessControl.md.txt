# AMO Access Control Foundation

## Current client-side policy

AMO now uses an explicit workspace-claim and minimal RBAC model:

- everyone, including anonymous users, can read the workspace;
- an unclaimed workspace is read-only;
- any Google-authenticated user can explicitly Claim Workspace;
- claiming creates or binds an authoritative AMO User and grants that User the `admin` role;
- after claim, authenticated users do not receive write access merely by signing in;
- only enabled, mapped AMO Users with an assigned role or capability can write;
- the same client capability checks apply to Local and Remote Workspace modes.

Remote Workspace API authorization is not yet the security boundary. Server-side enforcement will be added separately; the current model is application/client enforcement and defence in depth.

## Bootstrap claim

Claim is intentionally explicit rather than automatic first-login ownership.

The Users page shows Claim Workspace only while `accessControl.claimed !== true`. The claimant must be signed in with Google and supply their Company / Entra account. Claiming persists:

```json
{
  "accessControl": {
    "claimed": true,
    "claimedAt": "...",
    "claimedByUserId": "user-stable-id",
    "writeRequiresMapping": true
  }
}
```

and creates or updates the claimant User with:

```json
{
  "roles": ["admin"]
}
```

Claim is a bootstrap mechanism only. There is no permanent special Owner permission: after claim the ordinary role/capability model applies. A claimed workspace must always retain at least one enabled Admin.

For Remote Workspace the later server implementation must make claim atomic so two users cannot claim concurrently. Local Workspace remains a cooperative application boundary.

## Roles

Roles are source-controlled application definitions rather than editable configuration.

### Read-Write User (`contributor`)

The normal operational role grants:

- `demand.write`
- `allocation.write`
- `people.write`
- `ideas.write`
- `status.update`

All read capabilities remain implicit for everyone.

### Admin (`admin`)

Admin grants every current write capability, including the Read-Write User capabilities plus:

- `status.publish`
- `system.configure`
- `users.manage`
- `system.restore`

Admins can add Users, map authentication identities, grant or remove roles, and grant additional capabilities.

## Capability vocabulary

The source-controlled vocabulary currently includes:

- `workspace.read`
- `workspace.write` (aggregate compatibility check: true when the User has any write capability)
- `workspace.claim`
- `demand.read`
- `demand.write`
- `allocation.read`
- `allocation.write`
- `people.read`
- `people.write`
- `ideas.read`
- `ideas.write`
- `status.read`
- `status.update`
- `status.publish`
- `financial.read`
- `system.configure`
- `users.manage`
- `system.restore`

Feature UI asks `amoAccess.can(capability)` rather than testing Google authentication directly. This lets the capability vocabulary later gain Department / Team scopes without replacing feature code.

## Authoritative Users

Admin -> Users is the authoritative application identity store and remains deliberately separate from existing People records.

```text
User
  -> canonical company identity
  -> authentication identities (Google now, Entra later)
  -> roles
  -> additional capabilities

Team Member (future People refactor)
  -> userId
  -> teamId
  -> roleId
  -> FTE / capacity metadata
```

Example persisted User:

```json
{
  "id": "user-stable-id",
  "displayName": "Some Body",
  "companyAccount": "some.body@company.com",
  "enabled": true,
  "roles": ["contributor"],
  "capabilities": ["status.publish"],
  "identities": [
    {
      "provider": "google",
      "subject": "google-immutable-subject-id",
      "email": "somebody@gmail.com",
      "enabled": true
    }
  ]
}
```

`companyAccount` is the canonical work identity for future ownership, audit and Entra linkage. Google is an authentication binding only. The immutable provider `subject` is preferred for identity resolution; Google email is retained as an administrative aid and bootstrap fallback.

## Local versus Remote Workspace

Client-side capability control applies to both workspace modes. In Local Workspace it disables mutation UI and guards application persistence, but a person with direct filesystem access can still modify the JSON outside AMO.

For Remote Workspace these checks improve UX and prevent the normal application from issuing operations the User is not entitled to perform, but they are not a security boundary. The API must later independently authenticate the Google token, resolve the same canonical AMO User and enforce the same capability decision. The planned API split is:

- `/api/public/*`: anonymous read operations;
- `/api/private/*`: authenticated/authorized mutation operations.

Read filtering/redaction, when introduced for sensitive data such as financial information, must also be enforced by the API rather than relying on browser hiding.

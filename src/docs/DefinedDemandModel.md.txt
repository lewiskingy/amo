# Defined Demand model reference

## Defined Demand (persisted entity: Demand)

### Required at initial creation

- `id` — generated stable AMO identifier;
- `title` — concise description of the managed body of Architecture demand;
- `businessArea` — business context;
- `status` — Demand State, defaulted by AMO (normally Assessing).

Only Title and Business Area require user input to create the record.

### Optional / progressively enriched

- `initiative` — portfolio grouping;
- `teamId` — Owning Team; may remain unassigned during early visibility;
- `priority` — portfolio priority;
- `ownerId` — Architecture Owner accountable for the Defined Demand;
- `initialEstimate.size` — XS/S/M/L/XL;
- `initialEstimate.estimatedDays` — snapshotted default ROM for the chosen size;
- `budgetForecast.estimatedDays` — current effort forecast used for budgetary and portfolio-planning purposes;
- `projectNumber` — optional Oracle Project Number for Actuals reconciliation;
- `health` — portfolio delivery health once meaningful;
- `context` — Summary / Context for why the Defined Demand exists;
- `source` — Front Door provenance/reference;
- funding/planning metadata owned by the existing Demand planning capability.

### Demand Budget Forecast

`budgetForecast.estimatedDays` is deliberately separate from the ROM and from the resource plan.

It answers: **what effort do we currently forecast this Demand will require for budgetary/planning purposes?**

It is not an approved budget and it is not changed automatically when Work Package estimates or named-resource allocations change. Reporting can compare the Budget Forecast with Work Package estimates and the rolled-up resource plan without conflating those measures.

### Derived, not authored on Demand

- Work Package count;
- current refined estimated effort = sum of child `estimatedEffortDays` values that exist;
- delivery start = earliest child `targetStart`;
- delivery end = latest child `targetEnd`;
- Work Package Service mix;
- Demand resource plan = sum of child Work Package allocations, plus any explicitly retained legacy undecomposed allocations during transition.

### Removed from the current Demand model

- `service` — now Work Package Service;
- `triage.romDays` / complexity — replaced by Initial Size + snapshotted ROM;
- nested `workPackage.scope` — delivery scope belongs to Work Package; useful parent text migrates to `context`;
- nested `workPackage.architectureOwner` — becomes parent `ownerId`;
- nested `workPackage.targetStart` / `targetEnd` — Work Package dates only;
- nested Demand work-package governance/delivery metadata — retired from current Demand;
- `deliverables[]` — not converted into Work Packages automatically;
- Demand-level Azure DevOps linkage — retired in Step 3;
- Cost Centre / Project Code — never promoted to Project Number.

Removed legacy values may be retained under `legacy` for audit/history but do not drive current planning or reporting.

## Work Package

### Required

- `id` — generated stable Work Package identifier;
- `demandId` — parent Defined Demand;
- `title`;
- `service` — Architecture Service;
- `status` — Work Package delivery state.

### Optional delivery detail

- `description` — delivery scope;
- `acceptanceCriteria`;
- `estimatedEffortDays` — refined package estimate;
- `targetStart`;
- `targetEnd`;
- `azureDevOpsWorkItemId`.

Work Package owns the delivery planning level at which named people are allocated. Actuals do not move to Work Package level: Oracle Actuals remain reconciled to parent Demand through Project Number.

## Allocation

Steady-state Allocation is:

```text
Person × Work Package × Month
```

An allocation retains both:

- `demandId` — required parent Demand context;
- `workPackageId` — the delivery package being resourced;
- `teamMemberId` — Person;
- `forecast` — monthly fraction of the Person's available FTE.

The referenced Work Package must belong to the referenced Demand. `demandId` is retained rather than inferred so validation, querying and Demand reporting remain simple and explicit.

Pre-existing records without `workPackageId` remain readable as **legacy undecomposed allocations**. They are not silently assigned to a Work Package. During transition they continue contributing once to the parent Demand resource plan until the user explicitly decomposes them.

## Measurement progression

```text
Demand ROM Estimate
        ↓
Demand Budget Forecast
        ↓ compare
Work Package Estimate
        ↓ compare
Work Package Resource Plan Allocations
        ↓
Actuals at Demand / Project level
```

These are not successive overwrites of one field:

- **Demand ROM Estimate** is the original baseline expectation;
- **Demand Budget Forecast** is the current effort forecast for budgetary/planning purposes, not an approved budget;
- **Work Package Estimate** describes the effort implied by defined delivery packages;
- **Work Package Resource Plan Allocations** are the named-person monthly plan and roll up to the Demand resource forecast;
- **Actuals** remain observed Oracle facts reconciled at Demand level through Project Number.

Each measure remains separately reportable so AMO can show meaningful planning variance rather than hiding it by moving the target.

# AMO Status Reporting

## Purpose

Status Reporting is the collaborative management-reporting layer for active Architecture Demand. It is not a replacement for Azure DevOps work-item workflow. The Status Report page is the authoring and lifecycle surface for the current reporting cycle; the report artefact itself is rendered consistently wherever it is viewed.

## Reporting-cycle lifecycle

AMO uses one active reporting cycle plus historical report snapshots.

```text
Draft
  | Publish
  v
Published
  | Unpublish
  +-----------------> Draft
  |
  | New Draft
  v
Final
  |
  +-----------------> next Draft
```

### Draft

`status-reports/draft.json` is the active working cycle. Multiple contributors may edit it. Draft narrative does not change Demand Health until the report is published.

### Published

Publish uses the latest committed Draft. The active cycle remains in `draft.json`, but becomes read-only and records `publishedReportId`, `publishedAt`, `publishedBy` and `revision`. A corresponding `SR-*.json` snapshot is written with state `Published`.

Published is intentionally reversible. **Unpublish** reopens the active cycle as Draft. Republishing updates the same report ID and increments its revision.

### Final

**New Draft** is the finalisation boundary. It changes the current Published snapshot to `Final` and creates the next `draft.json`. Final reports are historical and read-only.

## Status Report authoring page

The live **Status Report** page is deliberately focused on producing the report rather than duplicating the Dashboard. It contains:

- report lifecycle actions such as Edit Draft, Save Draft, Preview, Publish, Unpublish and New Draft;
- reporting progress and current-cycle state;
- the active-Demand authoring table with prominent Health semantics;
- a compact Latest Report entry point.

Dashboard-style Demand highlights, Capacity outlook, Portfolio forecast and Allocation outlook are **not rendered above the authoring table**. They are still captured into the report snapshot and appear when Previewing or viewing the report artefact.

The authoring table keeps strong Health cues because it is the working control surface for identifying items that are At Risk or Off Track and ensuring narrative is supplied.

## Report composition

The report artefact can include:

1. **Demand highlights** — headline Demand metrics captured for the reporting cycle;
2. **Capacity outlook** — FTE capacity and allocation position;
3. **Portfolio forecast** — best available total forecast;
4. **Allocation outlook** — phased allocation values;
5. **Architecture Status Report** — Demand-level Health and narrative.

Historical reports use the values persisted at publication time. Viewing or changing scope never recalculates a historical report from today's live workspace.

## One report renderer

`app-report-renderer.js` is the authoritative report presentation implementation. It owns:

- report structure;
- report-level presentation;
- Health semantics;
- report Health overview;
- scope projection;
- Dashboard snapshot sections;
- Demand narrative rendering.

Both in-application Preview/View and the lightweight `/reports` reader delegate to this renderer. The modal and standalone page are hosts only; they do not maintain competing report HTML implementations.

Legacy presentation compatibility assets must not reintroduce wrappers around `reportNarrativeHtml()`, `dashboardSnapshotHtml()` or `renderStatusReporting()` to create another report format.

## Health semantics and accessibility

Status Reporting uses the same controlled Health model as Demand:

- **On Track**
- **At Risk**
- **Off Track**

Health is never communicated by colour alone. The report renderer presents visible Health text, a semantic dot, a strong coloured rail and corresponding header treatment for each reported Demand item. A Health overview summarises the count in each state without inventing an overall report Health.

The Status Report authoring table uses its own compact Health-cell treatment appropriate to a working table.

## Scope model

Report viewing follows the organisation hierarchy:

```text
Department
  Organisation-wide
  or a specific Department

Team
  All teams / Whole department
  or a specific Team within the selected Department
```

Organisation-wide view always means all Teams. Selecting a specific Department enables the Team selector.

New report snapshots persist `departmentId`, `departmentName`, `teamId` and `teamName` on report entries so the lightweight viewer can scope an immutable report without loading current organisation configuration. Historical reports without all hierarchy metadata remain viewable; available filtering is limited to metadata that was persisted at the time.

Dashboard snapshots are persisted for organisation, Department and Team scopes where available. Scope projection chooses the matching persisted snapshot and filters report entries; it never reads the live Demand register.

## Preview, View and Open Report

AMO intentionally uses three user concepts:

- **Preview** — view the current Draft as a report inside AMO;
- **View** — view a Published or Final report inside AMO;
- **Open Report** — open a persisted report in the canonical lightweight report reader.

Preview and View use the same in-application modal host and the same `AmoReportRenderer` output. A persisted Published/Final report modal contains **Open Report ↗**.

Draft Preview has no persisted report identity, so it does not expose Open Report.

The application no longer provides dedicated **Copy Link**, **Copy Local Link**, **Print / Save PDF**, **Maximize** or generated standalone-window actions for reports. Browser-native address copying and printing remain available where appropriate.

## Canonical report route

Published and Final reports have the canonical route:

```text
/reports/{reportId}
```

For example:

```text
/reports/SR-20260828-153012
```

The route opens a lightweight report-only page. It does **not** call the AMO workspace `loadWorkspace()` path and therefore does not run workspace migrations, safety backups, archive maintenance, autosave or normal workspace startup. It resolves exactly one report through `WorkspaceRepository.getStatusReport(id)` and renders it with `AmoReportRenderer`.

### Remote workspace

A normal `/reports/{id}` route resolves through `RemoteWorkspaceRepository`. It uses the remembered Remote Workspace URL when available, otherwise the configured AMO API default.

### Local workspace

A persisted Local Workspace report opens as:

```text
/reports/{reportId}?source=local
```

The URL does not encode a filesystem path. The report viewer reuses the remembered File System Access directory handle in browser IndexedDB. If permission is no longer active, the viewer offers **Reconnect Remembered** or **Choose Workspace** and still loads only the requested report.

## Status Report History

History exposes one primary action per report: **View**. This opens the shared in-application viewer. From there the reader can choose **Open Report ↗** when a standalone report page is needed.

Latest Report follows the same interaction model.

## Collaborative draft saves

Editing remains optimistic. Save Draft acquires the short-lived `status-report--draft` commit lock, rereads the latest shared draft, performs the existing entry/field-level three-way merge and writes only when there is no conflicting concurrent edit.

Publish, Unpublish and New Draft continue to use the same lifecycle locking behaviour.

## Persistence model

Typical status-report storage:

```text
status-reports/
  draft.json                 active cycle: Draft or Published
  SR-YYYYMMDD-HHMMSS.json   Published or Final snapshot
```

During Unpublish, the corresponding snapshot is temporarily marked `Unpublished` while `draft.json` returns to Draft. It is not shown as normal report history. Republishing updates that same snapshot back to Published. New Draft changes it to Final.

# AMO Status Reporting

## Purpose

Status Reporting is the collaborative management-reporting layer for active Architecture Demand. It is a narrative/Health control surface, not a replacement for Azure DevOps work-item workflow and not a second Dashboard.

The Status Report page is the authoring/lifecycle surface for the current reporting cycle. Preview, Published and Final report artefacts use the canonical report renderer and immutable snapshot data.

## Reporting-cycle lifecycle

```text
Draft
  | Publish
  v
Published
  | Unpublish
  +-----------------> Draft
  |
  | New Draft
  v
Final
  |
  +-----------------> next Draft
```

`status-reports/draft.json` is the active cycle. Publish creates/updates the corresponding `SR-*.json` immutable report snapshot. Unpublish reopens the active cycle. New Draft finalises the current Published report and starts the next cycle.

## Authoring surface

The live Status Report page is intentionally focused on producing the report. It contains lifecycle actions, reporting progress and the active-Demand authoring table with strong Health cues.

Dashboard-style portfolio metrics are not rendered above the authoring table. The authoring surface should make it easy to identify At Risk/Off Track Demand and supply narrative without duplicating resource-management views.

## Canonical report semantics

Published/Preview reporting must use the same reporting semantics as Dashboard, Resource Plan and Defined Demand. Calculations belong to `ReportingModel`; report views must not introduce their own competing effort/cost formulas.

The important measures are:

- **Initial ROM** — original Defined Demand assessment baseline; indicative £ uses the configured blended/default day rate.
- **Work Package Estimate** — current sum of populated WP estimates plus estimate coverage; indicative £ uses the blended/default rate.
- **Allocation Forecast** — named resource plan, where FTE = allocation fraction × Person FTE and forecast £ uses the Person Role day rate/fallback rate.
- **Actual effort/cost** — imported Oracle hours and Cost in GBP; Actual cost is authoritative and is never recalculated from AMO Role rates.
- **Projected effort/cost** — Actual to date + remaining Allocation Forecast.

Where a reporting period has imported Actuals, Actuals are the reported measure for that period. Allocation remains the planning baseline for variance comparison.

AMO never infers Work-Package-level Actuals from Project/Demand Actuals.

## Work Package delivery context

Service, delivery status, refined estimate and target dates are Work Package concerns. Defined Demand does not regain a current `service` field for reporting.

A report snapshot may carry the derived list of child Work Package services and other derived delivery context so readers can understand the Demand. This is immutable snapshot context, not an authored Demand Service.

Detailed Work Package scope and acceptance criteria remain in the authoritative delivery backlog and are not copied into status reports by AMO.

## Capacity and recovery context

Portfolio snapshots can include concise resource-owner context using the canonical model:

- available capacity in FTE/days/value;
- forecast recovery on Project-backed Demand;
- Actual recovery from imported Oracle cost;
- utilisation/variance attention signals.

Project Number is the current cross-charge/reconciliation indicator; reporting does not invent a separate recoverable flag.

The same imported monetary fact may be labelled **Actual cost** in a Demand view and **Actual recovery** in a resource-owner view.

## Report composition

A report artefact can contain:

1. concise portfolio/Demand highlights;
2. capacity/recovery snapshot where useful;
3. Architecture Status Report narrative and Health;
4. Work Package-derived service/delivery context for each Demand where captured.

Historical reports use values persisted at publication time. Changing today's workspace or scope does not recalculate an older report.

## One report renderer

`app-report-renderer.js` is the authoritative report presentation implementation. It owns report structure, report-level presentation, Health semantics, scope projection, immutable snapshot sections and Demand narrative rendering.

Both in-application Preview/View and the lightweight `/reports` reader delegate to this renderer. Hosts must not maintain competing report HTML implementations or reimplement reporting calculations.

## Health semantics and accessibility

Status Reporting uses the same controlled Health model as Demand:

- **On Track**
- **At Risk**
- **Off Track**

Health is never communicated by colour alone. The renderer presents visible text and semantic visual treatment. The authoring table retains a compact Health treatment appropriate to working data entry.

## Scope model

Report viewing follows the organisation hierarchy: Organisation/Department and optional Team scope. Preview/View maintains its own report scope state and does not alter the surrounding AMO page scope.

New snapshots persist Department/Team identifiers and names on entries so immutable historical reports can be scoped without reading today's organisation configuration. Historical reports remain viewable even where older snapshots contain less hierarchy metadata.

## Preview, View and Open Report

- **Preview** — view the current Draft as it would be published.
- **View** — view a Published or Final report inside AMO.
- **Open Report** — open the same canonical presentation in the lightweight reader.

Published/Final routes use `/reports/{reportId}` with optional `department` and `team` query parameters. Draft standalone preview uses the existing temporary one-time browser preview snapshot and `/reports/preview` route; it is not persisted to report history.

## Status Report History

History exposes Published/Final snapshots. Latest Report is the shortcut to the most recent published artefact; History remains the catalogue for earlier reports.

## Collaboration and persistence

Draft saves continue to use optimistic entry/field-level merge and the status-report draft lock. Publish, Unpublish and New Draft retain their existing lifecycle locking behaviour.

Typical storage remains:

```text
status-reports/
  draft.json
  SR-YYYYMMDD-HHMMSS.json
```

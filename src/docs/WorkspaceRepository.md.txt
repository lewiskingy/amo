# AMO Workspace Repository

## Purpose

AMO application and domain logic should not depend directly on the browser File System Access API or on a REST transport. Persistence is accessed through a WorkspaceRepository contract.

The current implementations are LocalWorkspaceRepository and RemoteWorkspaceRepository. The local implementation preserves the folder-backed JSON workspace; the remote implementation maps the same application-facing capabilities to the AMO HTTP API.

## Layers

```text
AMO UI / domain logic
        |
        v
amoWorkspace / WorkspaceRepository contract
        |
        +-- LocalWorkspaceRepository
        |       -> Browser File System Access API
        |       -> JSON workspace
        |
        +-- RemoteWorkspaceRepository
                -> REST API
                -> server-side workspace service
                -> filesystem repository
```

`workspaceHandle` remains as a compatibility value for the local UI and remembered-folder feature. New persistence code should use `amoWorkspace` or the active `workspaceRepository`, not navigate the handle directly.

## Common record capabilities

The repository exposes common operations for normal entities:

- `listRecords(type)`
- `getRecord(type, id)`
- `saveRecord(type, record)`
- `deleteRecord(type, id)`
- `getSettings()`
- `saveSettings(settings)`

The current entity types are `demand`, `team`, `allocations` and `ideas`.

Workspace load/save also has a batch-oriented `loadWorkspace()` / `saveChanges()` path. This preserves AMO's dirty-record autosave behaviour and avoids unnecessary writes. A remote implementation may translate this into individual REST calls or a bulk endpoint without exposing that decision to the UI.

## Named business/storage capabilities

Operations that are not ordinary CRUD have explicit repository methods:

- status report catalogue, read and write;
- cooperative and short-lived commit locks;
- archive movement;
- safety backup creation, listing and retention pruning.

These methods are intentionally capability-based. A remote backend does not need to reproduce local filesystem mechanics; it only needs to provide the same outcome.

For example, `listStatusReports()` is implemented locally by listing JSON filenames. The remote implementation maps status-report reads/writes to `/api/status-reports` endpoints.

## Status Reporting persistence

Status Reporting uses `status-reports/draft.json` as the active reporting cycle and `SR-*.json` as report snapshots. The active cycle can be Draft or Published. New Draft finalises the current Published snapshot and starts the next cycle with a previous-report baseline.

Collaborative Draft editing uses optimistic concurrency rather than a long-held workspace lock. Edit captures a baseline; Save Draft acquires a short-lived `status-report--draft` commit lock, rereads the latest `draft.json`, and performs a three-way merge of baseline/local/latest values at report-entry field level. Non-conflicting changes merge automatically. If two users changed the same field on the same Demand entry, the write is rejected for user reconciliation.

Publish, Unpublish and New Draft use the same short-lived commit-lock resource so lifecycle transitions cannot race a concurrent Draft commit. See `StatusReporting.md.txt` for the lifecycle and data semantics.

## Compatibility bridge

`app-workspace-repository-bridge.js` redirects older modules such as Status Reporting, locking and backup inventory through the repository contract without changing their public/domain functions. It also exposes the small `amoWorkspace` facade for new application code.

This bridge is transitional. As modules are subsequently refactored, direct compatibility hooks can be removed rather than expanded.

## Local repository

`LocalWorkspaceRepository` owns the File System Access API mechanics for:

- loading `workspace.json`, configuration and active entity records;
- dirty-record saves and deletes;
- status-report lazy loading and persistence;
- lock persistence;
- archive writes/removal of active records;
- safety backup creation and retention.

The existing JSON layout and backup/archive semantics are intentionally retained.

## Remote implementation

`RemoteWorkspaceRepository` implements the same contract over HTTP. Current server capabilities map broadly to:

```text
workspace metadata / settings
entity CRUD
status report catalogue / draft / publish lifecycle storage
short-lived commit locking
maintenance / archive
```

The remote API exposes domain capabilities rather than requiring application code to know filesystem mechanics. The server can later replace its storage implementation while retaining the HTTP and client repository contracts.

## Refactor rule

When adding new AMO features:

> UI and domain code may ask the repository to perform a persistence capability, but should not know how or where that capability is stored.

Simple data uses CRUD-style methods. Multi-record or business transactions should gain explicit named operations where needed rather than being orchestrated as ad-hoc filesystem operations in the UI.

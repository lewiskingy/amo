# Defined Demand and Reporting Acceptance

Validate this candidate against both Local and Remote/Test workspaces before promotion.

## 1. Demand planning model

Create or open a Defined Demand with:

- Initial ROM;
- Budget Forecast;
- at least two Work Packages;
- Work Package estimates;
- named-person resource allocations;
- Project Number and imported Actuals where available.

Confirm Initial ROM, Budget Forecast, Work Package Estimate, Resource Plan and Actual/Projected effort remain separate measures and never overwrite one another.

Budget Forecast must be described as the current forecast for budgetary/planning purposes. It must never be presented as an approved financial budget or authorisation to spend.

## 2. Work Package resource planning

Confirm new allocations are created only as:

```text
Person × Work Package × Month
```

and retain the correct parent `demandId`.

For existing Demand-only allocation records, confirm:

- they remain visible as **legacy / undecomposed**;
- they continue to contribute once to Demand totals;
- AMO never guesses a Work Package;
- the user can explicitly assign them to a valid child Work Package;
- person and monthly forecast values remain unchanged when the Work Package is assigned.

A Work Package from another Demand must be rejected.

## 3. Allocation FTE semantics

Create People with different FTE values, including 0.8 or 0.5 FTE.

Confirm:

- allocation percentage is interpreted against Person available FTE;
- 100% allocation for a 0.8 FTE Person reports 0.8 FTE, not 1.0 FTE;
- Resource Plan and Dashboard use the same canonical calculation;
- Demand Resource Plan totals equal the roll-up of child Work Package allocations plus any transitional undecomposed allocation.

## 4. Work Package estimate and Resource Plan

For a Demand with multiple Work Packages, confirm:

- WP Estimate sums only populated child estimates;
- estimate coverage remains visible;
- each Work Package reports its own Estimate and Resource Plan;
- Demand reports the rolled-up WP Estimate and rolled-up Resource Plan;
- changing a WP estimate does not change Budget Forecast;
- changing allocations does not change Budget Forecast.

## 5. Actuals boundary

Confirm Oracle Actuals continue to reconcile through:

```text
fact.projectNumber -> Demand.projectNumber
fact.staffNumber   -> Person.staffNumber
```

No Work-Package-level Actual is inferred.

In Work Package resource detail for an imported Actual period, the retained allocation plan may be shown, but the UI must state that Actuals are held at the parent Demand rather than repeating Demand Actuals as WP Actuals.

## 6. Demand reporting progression

Open a Demand with complete planning context and confirm the record view shows:

```text
Initial ROM
Budget Forecast
WP Estimate
Resource Plan
Actual to date
Projected effort
```

Confirm Projected is:

```text
Actual to date + remaining Allocation Forecast
```

and is compared with Budget Forecast using language such as **above Budget Forecast**, never “over budget”.

## 7. Management signals

Create scenarios that exercise the shared materiality threshold and confirm AMO surfaces appropriate signals for:

- missing Budget Forecast;
- Budget Forecast with no Work Packages;
- incomplete WP estimate coverage;
- WP Estimate materially above/below Budget Forecast;
- Resource Plan materially above/below Budget Forecast;
- Projected effort materially above/below Budget Forecast;
- legacy undecomposed allocations.

Signals are management prompts, not accounting assertions.

## 8. Resource Plan

Confirm Resource Plan still presents canonical capacity, Actual/Forecast basis, Person utilisation and recovery information.

Confirm it also presents a Demand planning-position view with:

- ROM;
- Budget Forecast;
- WP Estimate;
- Resource Plan;
- Actual to date;
- Projected effort;
- material planning position.

Work Package resource detail must show the Work Package lineage for named-person allocations.

`src/app-resource-plan.js` remains the sole owner of `renderResource`; planning integration modules must not replace it or recreate quantitative Actual/Forecast formulas.

## 9. Dashboard

Confirm the existing Attention Required surface includes material above-Budget-Forecast signals and legacy allocation-decomposition signals without replacing the existing health/capacity attention rules.

## 10. Status Reporting

Open Status Report authoring and confirm:

- narrative/Health authoring remains primary;
- each Demand shows a concise planning position;
- Preview/Publish persists a report-time planning snapshot;
- published historical reports render their persisted planning values rather than reading current live values;
- older immutable snapshots without planning context remain readable;
- no Work Package Actuals are invented in the report.

## 11. Roadmap

Confirm delivery windows remain derived from Work Package target dates.

The resource line must represent the resource plan rolled up from Work Package allocations to parent Demand. Legacy undecomposed allocations may contribute during transition but must not be described as the steady-state model.

## 12. Financial semantics

Confirm:

- named Resource Plan Forecast uses Person Role day rate with blended/default fallback;
- Initial ROM, Budget Forecast and Work Package Estimate may use blended/default rate only for indicative valuation;
- imported Oracle `actualCostGbp` remains authoritative;
- indicative Budget Forecast value is not presented as an approved accounting budget.

## 13. Canonical implementation / no duplicate model

Inspect the active code path and confirm:

- `app-reporting-model.js` owns quantitative Actual/Forecast arithmetic;
- `app-planning-reporting.js` owns planning progression comparisons and planning management signals;
- `app-resource-plan.js` remains the sole Resource Plan renderer;
- `app-planning-reporting-ui.js` consumes canonical contexts rather than recalculating FTE/days/cost;
- `app-planning-reporting-hooks.js` contains lifecycle/presentation integration only;
- no active creation path creates a new Demand-level person allocation;
- documentation no longer describes steady-state allocation as Person × Defined Demand × Month.

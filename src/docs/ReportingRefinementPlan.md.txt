# Reporting Refinement — Current Semantics

## Purpose

AMO reporting keeps planning, delivery and observed effort as separate measures and presents them as one management progression:

```text
Initial Demand ROM
        ↓
Demand Budget Forecast
        ↓ compare
Work Package Estimate
        ↓ compare
Work Package Resource Plan
        ↓
Actual to date + remaining Resource Plan
        = Projected effort
```

These values answer different questions and must never overwrite one another.

## Canonical measures

### Initial ROM

The assessment-time baseline held on `Demand.initialEstimate`. It remains separately reportable after later estimates and forecasts change.

### Demand Budget Forecast

The current forecast of expected Demand effort for budgetary and portfolio-planning purposes. It is **not** an approved financial budget, authorisation to spend, or named-person resource allocation.

Budget Forecast may change as understanding improves. Changing it does not automatically change Work Package estimates or allocations.

### Work Package Estimate

The current delivery estimate is the sum of populated child `estimatedEffortDays`. Reporting also retains estimate coverage so partially estimated decomposition is never presented as complete.

### Work Package Resource Plan

Steady-state allocations are:

```text
Person × Work Package × Month
```

`demandId` is retained as parent context and Demand Resource Plan totals are derived by rolling up child Work Package allocations. Existing Demand-only allocations are supported only as explicit legacy/undecomposed transition records.

Allocation values are fractions of the Person's available FTE:

```text
Forecast FTE = allocation fraction × Person FTE
Forecast days = Forecast FTE × working days in month
Forecast cost = Forecast days × Person Role day rate
```

### Actual Effort / Cost

Oracle Actuals remain authoritative observations at Demand/Project level:

```text
Person × Project Number × Month
        ↓
Demand.projectNumber
```

AMO does not infer Work-Package-level Actuals. In Work Package detail, Actual periods therefore retain the WP plan but explicitly state that Actuals are held at the parent Demand.

### Projected effort / cost

Across the reporting horizon:

```text
Actual to date
+ remaining Allocation Forecast for non-actualised periods
= Projected total
```

Projected effort is compared with Demand Budget Forecast. It is not described as being “over budget”; the correct language is **above Budget Forecast**.

## Canonical planning context

`src/app-planning-reporting.js` composes the cross-domain management context while `src/app-reporting-model.js` remains authoritative for quantitative Actual/Forecast arithmetic.

The canonical Demand context contains:

- ROM days;
- Budget Forecast days;
- Work Package Estimate days + estimate coverage;
- Resource Plan days;
- Actual days to date;
- remaining Resource Plan;
- Projected days;
- ROM → Budget Forecast comparison;
- WP Estimate → Budget Forecast comparison;
- Resource Plan → Budget Forecast comparison;
- Resource Plan → WP Estimate comparison;
- Projected → Budget Forecast comparison;
- legacy undecomposed allocation count.

The canonical Work Package context contains:

- Work Package Estimate;
- Work Package Resource Plan;
- Resource Plan → Estimate comparison.

## Management signals

Planning signals use the shared material-variance threshold from ReportingModel. Initial management classifications include:

- Budget Forecast not set;
- Budget Forecast exists but no Work Packages are defined;
- incomplete Work Package estimate coverage;
- WP Estimate materially above/below Budget Forecast;
- Resource Plan materially above/below Budget Forecast;
- Projected effort materially above/below Budget Forecast;
- legacy allocation not assigned to a Work Package.

These are management prompts, not accounting assertions.

## Reporting surfaces

### Defined Demand

The Demand record view shows the complete planning progression and any material planning signals. Budget Forecast is explicitly described as a planning forecast rather than an approved budget.

### Resource Plan

`src/app-resource-plan.js` remains the sole Resource Plan renderer and owner of capacity/Actual/Forecast presentation. The planning-reporting integration adds a Demand planning-position table and a Work-Package-aware resource detail using canonical PlanningReporting contexts.

Work Package resource detail does not repeat parent Demand Actuals as though they were WP Actuals. For imported periods, the retained allocation plan is shown with the statement that Actuals are held at Demand.

### Dashboard

Dashboard remains concise. Material above-Budget-Forecast signals and legacy allocation-decomposition signals are added to the existing attention surface.

### Status Report

Status authoring remains narrative/Health focused, with concise planning position shown alongside each Demand. Preview/Published snapshots persist report-time planning context so historical reports do not read live current planning values later.

### Roadmap

Roadmap remains temporal. Work Package dates define the delivery window. The resource line is the roll-up of Work Package Resource Plan allocations to parent Demand; legacy undecomposed allocations remain transitional only.

## Financial semantics

- Initial ROM, Budget Forecast and Work Package Estimate may use the configured blended/default day rate for indicative valuation.
- Named Resource Plan Forecast uses Person Role rates, falling back to the blended/default rate.
- Imported Oracle Actual cost remains authoritative.

An indicative Budget Forecast value must never be presented as an approved accounting budget.

## Ownership and implementation

- `src/app-reporting-model.js` — Actual/Forecast arithmetic, FTE, days, cost, capacity, Actual-period precedence and existing variance signals.
- `src/app-planning-reporting.js` — canonical planning progression, cross-measure comparisons and planning management signals.
- `src/app-resource-plan.js` — sole Resource Plan renderer.
- `src/app-planning-reporting-ui.js` — shared presentation helpers for the planning progression across Demand, Resource Plan and Status Reporting; it does not replace `renderResource`.
- `src/app-planning-reporting-hooks.js` — lifecycle/late-load integration and Dashboard attention enrichment; it does not define reporting arithmetic.

## Regression invariants

Tests must protect these rules:

- ROM, Budget Forecast, WP Estimate and Resource Plan remain independent facts;
- Budget Forecast is never labelled as approved budget;
- new allocations target Work Packages;
- Demand resource totals are roll-ups, with legacy Demand-only allocation supported only during transition;
- allocation percentage is multiplied by Person FTE;
- Actual-period-wins semantics remain intact;
- projected total is Actual + remaining forecast;
- no Work Package Actuals are inferred;
- Project Number remains the Actuals/recovery reconciliation boundary;
- Status snapshots persist report-time planning context;
- `app-resource-plan.js` remains the sole owner of `renderResource`;
- planning integration modules consume canonical models rather than recreating quantitative formulas.

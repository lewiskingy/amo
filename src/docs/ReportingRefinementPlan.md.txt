# Reporting Refinement — Implemented Semantics

Status: implemented for Issue #121 Step 5.

## Purpose

AMO reporting uses one canonical semantic model across Dashboard, Resource Plan, Defined Demand and Status Reporting. The application deliberately keeps four different measures because they answer different questions:

```text
Initial Demand ROM
        ↓
Work Package Estimated Effort
        ↓
Allocation Forecast
        ↓
Actual Effort / Cost
```

These values must not be silently substituted for one another.

## Canonical measures

### Initial ROM

Initial Size and snapshotted Initial ROM days preserve the assessment-time expectation for Defined Demand. Later Work Package estimates do not overwrite this baseline.

Financial display is indicative:

```text
Initial ROM days × configured default/blended day rate
```

### Work Package Estimate

Current delivery estimate is the sum of populated child `estimatedEffortDays`. Reporting always retains estimate coverage (for example 3/5 Work Packages estimated) so incomplete decomposition is not presented as a complete estimate.

Financial display is indicative and uses the configured default/blended day rate because the estimate does not identify the eventual person/Role mix.

### Allocation Forecast

Allocation is the resource plan at Person × Defined Demand × Month.

An allocation value is a fraction of the person's available FTE, therefore:

```text
Forecast FTE = allocation fraction × Person FTE
Forecast days = Forecast FTE × working days in month
Forecast cost = Forecast days × Person Role day rate
```

If the Role has no configured rate, the default/blended day rate is the fallback.

This correction is important for part-time People: a 100% allocation for a 0.8 FTE Person contributes 0.8 FTE, not 1.0 FTE.

### Actual Effort / Cost

Oracle Actuals remain authoritative observations.

```text
Actual days = imported Actual hours ÷ standard hours per day
Actual FTE = imported Actual hours ÷ full-time working hours for the month
Actual cost/recovery = imported Oracle Cost in GBP
```

AMO never recalculates imported Actual cost from Role rates.

Actuals reconcile to Defined Demand through `Demand.projectNumber` and to People through Staff Number. AMO does not manufacture Work-Package-level Actuals.

### Reported effort

For one month:

```text
Actual effort/cost when the Actuals period exists
otherwise Allocation Forecast effort/cost
```

Allocation remains visible as the plan when Actuals exist so variance can still be understood.

### Projected effort / cost

Across the reporting horizon:

```text
Actual to date
+ Allocation Forecast for non-actualised periods
= Projected total
```

Projected resource effort is not the same thing as Work Package Estimate.

## Capacity and recovery

Available capacity is derived from active People:

```text
Available FTE = Person FTE
Available days = Person FTE × working days
Capacity value = available days × Role day rate
```

A missing Role rate falls back to the configured blended/default rate.

Project Number is the current cross-charge/reconciliation indicator; there is no separate Demand-level recoverable flag.

- **Forecast recovery** — forecast allocation value on Project-backed Defined Demand.
- **Actual recovery** — imported Oracle cost on Project-backed Defined Demand.
- **Billable capacity value** — theoretical value of available People capacity.

The same imported monetary fact may be labelled **Actual cost** at Demand level and **Actual recovery** from the resource-owner viewpoint. It is not duplicated or recalculated.

## Canonical implementation

`src/app-reporting-model.js` owns the reporting calculations. Views should consume it rather than recreate formulas.

It owns:

- period Actual/Forecast basis;
- FTE-scaled Allocation Forecast;
- working-day and effort-day conversion;
- Role/default-rate lookup and forecast valuation;
- imported Actual hours/cost;
- capacity FTE/days/value;
- Initial ROM and Work Package estimate valuation/coverage;
- Demand Actual-to-date, remaining plan and projected total;
- management/variance signals;
- portfolio capacity/recovery aggregation.

`src/app-organization-hierarchy-compat.js` uses the canonical allocation-FTE helper for scoped Dashboard capacity rather than summing raw allocation percentages.

## User-facing surfaces

### Resource Plan

Primary capacity/resource-owner surface. It shows:

- available capacity in FTE with days/£ context;
- reported Actual/Forecast effort in FTE, days and £;
- utilisation and over-capacity periods;
- Person-level Actual vs plan using canonical FTE scaling;
- allocation detail that distinguishes allocation percentage from equivalent FTE;
- capacity value, forecast recovery and Actual recovery.

### Defined Demand

Primary sponsor surface. The Demand effort/cost outlook presents:

```text
Initial ROM
WP Estimate + coverage
Actual to date
Remaining Allocation Forecast
Projected total
```

ROM/WP £ values are marked as indicative by their semantics; Actual £ is imported Oracle cost.

### Dashboard

Remains a concise portfolio/attention surface. Scoped capacity calculation uses the same FTE-scaled allocation semantics as Resource Plan.

### Roadmap

Remains temporal. Work Package dates define delivery windows and Demand allocations define resource windows. Step 5 does not turn Roadmap into a finance report.

### Status Reporting

Status authoring remains narrative/Health focused rather than another Dashboard. Published/Preview report snapshots retain immutable portfolio context and Work Package-derived service context. No Demand-level Service is reintroduced as a domain field.

## Configuration

Current reporting assumptions live under `settings.reporting`:

```json
{
  "standardHoursPerDay": 7.5,
  "defaultDayRate": 700
}
```

`standardHoursPerDay` converts imported Actual hours into comparable effort days/FTE.

`defaultDayRate` is the current blended estimate/fallback rate. It is not the retired legacy `financialPlanning.defaultDayRate` and does not restore the old Role-rate map.

## Regression invariants

Tests must protect these rules:

- allocation percentage is multiplied by Person FTE;
- a missing Role rate uses the default/blended rate;
- imported Actual cost is never recalculated;
- ROM and WP estimate remain distinct;
- WP estimate coverage is retained;
- Actual-period-wins semantics remain intact;
- projected total is Actual + remaining forecast;
- no Work Package Actuals are inferred;
- Project Number remains the Actuals/recovery reconciliation boundary.

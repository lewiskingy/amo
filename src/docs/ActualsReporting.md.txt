# Actuals Reporting

AMO keeps planning and observed effort as separate facts.

- **Demand ROM Estimate** is the immutable early estimate baseline.
- **Demand Budget Forecast** is the current effort forecast for budgetary/portfolio-planning purposes; it is not an approved budget.
- **Work Package Estimate** is the refined delivery estimate for a package.
- **Allocations** are the named-resource planning source of truth at Person × Work Package × Month in the steady-state model.
- **Actuals** are imported observed effort/cost from Oracle and remain reconciled at Demand/Project level.
- Reporting composes Actuals and Allocation Forecast month by month: if an Actuals period exists, that month uses Actuals; otherwise it uses Allocation Forecast.
- The calendar date does not move the cut-over. A future/non-imported month remains Forecast until an Actuals period exists.
- A loaded Actuals month is authoritative. If an individual has no Actual row in that period, their Actual effort is zero rather than silently falling back to Forecast.
- Imported Oracle `Cost in GBP` is authoritative Actual cost/recovery; AMO never recalculates it using Role rates.

## Source facts and dynamic reconciliation

The durable Actuals fact preserves Oracle source identities. AMO does not require a reimport merely because current workspace identity/configuration changes after the fact was stored.

The reconciliation keys are:

```text
fact.projectNumber -> Demand.projectNumber
fact.staffNumber   -> Person.staffNumber
```

`demandId` and `teamMemberId` are reporting-time relationships derived from those source keys when a stored period is read. Existing facts therefore begin contributing to the relevant Demand/Person as soon as a unique current mapping exists. For example, adding Project Number `11702` to a Demand immediately reconciles already-stored facts carrying `projectNumber: "11702"`.

The source keys take precedence over any historical `demandId` / `teamMemberId` values contained in an older stored fact. This keeps prior imports compatible while preventing stale import-time relationships from overriding the current workspace model. Read-time reconciliation does not rewrite the stored Oracle fact.

If more than one Demand has the same Project Number, or more than one Person has the same Staff Number, the relationship remains unresolved rather than selecting one arbitrarily. Correcting the duplicate causes the existing stored facts to reconcile automatically on the next read.

## Defined Demand and Project Number

Defined Demand does not have to be a formal Project and may exist before a Project Number is known.

Where work is charged through Oracle, Demand can hold an optional **Project Number**. This is the accounting/reconciliation reference used to attach Oracle Project Actuals to Defined Demand:

```text
Oracle Project Number -> Demand.projectNumber -> Defined Demand
```

Project Number is also the current indicator used by reporting to identify Project-backed/cross-charge Demand. AMO does not maintain a second `recoverable` flag.

Project Number is stored as a string so source identifiers are preserved exactly, while the current UI accepts digits only. It must not be assigned to more than one Demand. Legacy Cost Centre / Project Code values are not an Actuals mapping source and are not migrated into Project Number.

If Oracle Actuals contain a Project Number that is not currently mapped to Demand, retained facts remain without Demand attribution until a unique current mapping exists. Duplicate Demand Project Numbers are treated the same way: AMO surfaces the reconciliation problem rather than arbitrarily selecting one Demand.

## Identity and effort conversion

Oracle `People #` (or `Person #` in older exports) matches AMO Person `staffNumber`. Name matching is not used. Retained facts are resolved against the current Staff Number mapping whenever Actuals are read.

The current importer still curates the large Oracle download before persistence: rows for a Staff Number that is not in current AMO People are excluded unless the row is otherwise retained through the existing project-scope rules. Dynamic reconciliation can remap facts that were stored previously, but it cannot recover source rows that were never persisted; those require a later reimport once they are in scope.

Actual hours are converted using **Standard working hours per day** under Reporting assumptions (7.5 by default):

```text
Actual days = Actual hours / standard hours per day
Actual FTE = Actual hours / full-time working hours for the month
```

Person utilisation compares reported FTE with the Person's configured available FTE.

## Forecast effort and cost

Allocation values are fractions/percentages of the Person's available FTE, not absolute FTE values:

```text
Forecast FTE = allocation fraction × Person FTE
Forecast days = Forecast FTE × working days in month
Forecast cost = Forecast days × Person Role day rate
```

In the steady-state model each Allocation targets a Work Package and retains its parent `demandId`. Demand resource forecast is therefore the roll-up of all child Work Package allocations.

Pre-existing Demand-only allocation records without `workPackageId` remain readable as **legacy undecomposed allocations** during transition. They continue to contribute once to the parent Demand forecast until explicitly assigned/decomposed through the Work Package allocation UX. AMO must never silently guess a Work Package for a legacy allocation.

Where the Person's Role has no configured rate, the configured **Default / blended day rate** is used as the fallback.

The same blended/default rate values Demand ROM, Demand Budget Forecast and Work Package estimates because those measures do not identify a named Role/person mix. Their £ values are therefore indicative rather than approved financial budgets.

## Planning progression

Reporting deliberately keeps the stages of knowledge distinct:

```text
Demand ROM Estimate
    ↓
Demand Budget Forecast
    ↓ compare
Work Package Estimate
    ↓ compare
Work Package Resource Plan Allocations
    ↓
Actual Effort / Cost at Demand Project level
```

- **Demand ROM Estimate** preserves the early assessment expectation.
- **Demand Budget Forecast** is the current effort forecast used for budgetary/portfolio planning; it is not an approved budget and does not move automatically with the resource plan.
- **Work Package Estimate** is the sum of populated child package estimates; reporting retains estimate coverage.
- **Work Package Resource Plan Allocations** are the current named resource plan and roll up to the parent Demand resource forecast.
- **Actuals** are observed Oracle facts attached to Demand via Project Number; no Work Package Actual is inferred.

Useful comparisons therefore include:

```text
Work Package Estimate vs Demand Budget Forecast
Resource Plan Forecast vs Demand Budget Forecast
Resource Plan Forecast vs Work Package Estimate
```

Across a reporting horizon:

```text
Actual to date + remaining Resource Plan Forecast = Projected effort / cost
```

Projected resource effort is not the same measure as Work Package Estimate or Demand Budget Forecast.

## Management classifications

The shared Reporting Model owns the classifications so Dashboard, Resource Plan, Demand and Status Reporting do not invent different rules.

Initial materiality thresholds are:

- material Demand variance: 20%;
- low overall effort: less than 50% of planned total effort;
- redirected-effort eligibility: at least 80% of planned total effort was recorded overall, with material offsetting Demand shortfall/increase;
- over capacity: more than 110% of the Person's available FTE;
- minimum material effort: 0.1 FTE;
- effectively zero effort: less than 0.01 FTE.

The classifications are:

- **No Actuals against plan** — material planned allocation but effectively no Actual effort overall.
- **Low overall effort** — materially less total effort recorded than planned.
- **Effort redirected** — total effort broadly matches plan but material shortfall on one Demand is offset by increased effort elsewhere.
- **Unplanned Demand effort** — Actual effort recorded against known Demand without a corresponding resource allocation for the period.
- **Over capacity** — total Actual effort exceeds the configured capacity threshold.
- **Unmapped project facts** — known-Person Actuals cannot be mapped unambiguously to AMO Demand.

AMO does not infer why effort moved. Status commentary is where the business reason is recorded.

## Views

### Resource Plan

Resource Plan is the detailed capacity/resource-owner view. It presents available and reported capacity in FTE with days/£ context, Person utilisation, Actual-versus-plan variance, allocation detail, and capacity/recovery information. Forecast allocation displays both the allocation percentage and its FTE-scaled equivalent.

The steady-state allocation hierarchy is Demand → Work Package → Person. Demand-level resource totals are roll-ups, not separately authored person allocations.

### Dashboard

Capacity Outlook uses Actual effort for loaded periods and Forecast elsewhere. Organisational scope uses the same canonical FTE-scaled allocation calculations as Resource Plan rather than summing raw allocation percentages.

### Defined Demand

The Demand effort and cost outlook should retain these measures separately:

- Demand ROM Estimate — days + indicative £;
- Demand Budget Forecast — days + indicative £ for budgetary planning, explicitly not approved budget;
- Work Package Estimate — days + indicative £ + estimate coverage;
- Actual to date — effort days + imported Oracle £;
- Remaining Resource Plan Forecast — effort days + forecast £;
- Projected total — Actual + remaining plan.

Actual-versus-plan management signals remain available alongside this progression.

### Status Report

The live Status Report remains a narrative/Health authoring surface rather than another Dashboard. Published/Preview snapshots preserve report-time portfolio context and Work Package-derived service context.

Service is not read from `Demand.service`. Current snapshots carry a `services` list derived from child Work Packages; the report renderer continues to understand older immutable snapshots that contain the legacy singular `service` field.

`app-report-renderer.js` is the canonical report renderer. It renders persisted report snapshot data and never reads live workspace Actuals.

## Forecast preservation

Actuals do not overwrite Allocations. Resource Plan Forecast remains available as the planning baseline for variance analysis even where the reported value for a period is Actual.

Actuals remain Demand/Project-level observations. AMO does not manufacture Work Package Actuals from the detailed Work Package Resource Plan.
